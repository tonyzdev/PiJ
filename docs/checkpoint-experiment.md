# Post-edit test selection experiment

This is an evaluation-only hypothesis: an automatic selector could replace some
main-model work choosing the next tests after an edit. Jev chooses from existing
files; a fixed program runs those tests; actual output is supplied before the
next provider request. Jev does not decide whether the change is correct.
Normal PiJ does not enable this extension.

## Frozen comparison

The first comparison uses one real PiJ decision-attribution repair, initialized
from public commit `4e1cdef` plus a byte-preserved patch generated by a prior real
`pij` run. The original 40 tests pass, but a visible real-SDK steering regression
fails. See the [fixture](../eval/checkpoint-fixture/README.md) for its independently
authored seven-check acceptance and seed/reference red-green evidence.

| Condition | Post-edit behavior |
| --- | --- |
| `manual` | Main model chooses when and which tests to execute. |
| `dependencies` | Program selects at most two tests by static relative-import distance to changed files, with path order breaking ties. |
| `jev` | One batched request ranks existing test files from bounded source changes, test names and imports; execute the top two. On provider failure, use the same dependency selector. |

Each condition runs the real `bin/pij.mjs` command using Sonnet 4.6 at medium
thinking, ordinary Jev integration off, and source briefing off. Limits are 48
provider requests, 1,600,000 reported tokens, 480 seconds and 16,384 output tokens
per request. Each receives identical task text, visible tests and dependency
lockfile. Code and build are frozen before launching the three candidates.
Each is one trajectory, not a replicated benchmark or causal effect estimate.

The automatic conditions inspect source/test changes once per completed tool
batch. No source change means no selection request. The same two-file limit and
12-second process deadline apply. Selection is scheduling, not test coverage:
names and imports do not establish assertions, and a passed checkpoint is never
complete acceptance. The model remains responsible for the full suite.

## Execution and evidence

```sh
node --env-file=.env --import tsx eval/checkpoint-run.ts --checkpoint manual
node --env-file=.env --import tsx eval/checkpoint-run.ts --checkpoint dependencies
node --env-file=.env --import tsx eval/checkpoint-run.ts --checkpoint jev
```

These commands make paid main-model requests; `jev` additionally makes live Jev
selection requests. Traces, checkpoint output and result metadata are private
under ignored `.pij/evals/`. The task clone receives only one reachable base
commit, the seed, task and visible regression. Holdout/reference assets and the
development checkout remain outside its permitted filesystem. Tests have
loopback access for deterministic SDK fixtures; no provider credentials.

The parent tracks detached checkpoint groups over a dedicated IPC channel and
terminates them on cancellation or CLI exit. Readiness is acknowledged before
the first model request. A context hook waits for the asynchronous checkpoint
and makes its actual output visible to the immediately following request.

After each candidate stops, independently run ordinary tests, the visible
regression, seven holdout tests, typecheck and build. Review its patch and docs.
Record acceptance, provider requests, wall time, reported usage/cost, automatic
test count/time, Jev success/fallbacks and whether the model still repeated tests.
Do not merge a generated patch merely because its own tests pass.

The useful comparison for Jev is against `dependencies`, as well as `manual`:
automatic testing alone may explain a gain. Conversely, redundant checks may
increase time and context without helping. A fast full-suite policy is another
plausible baseline and is not covered by this first three-condition experiment.

This run supplies a visible reproduction and enables medium thinking. Earlier
recovery runs lacked that reproduction and used thinking off, so their cost and
acceptance are not comparable to this protocol.
